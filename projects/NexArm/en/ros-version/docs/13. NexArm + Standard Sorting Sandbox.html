13. NexArm + Standard Sorting Sandbox ​

The NexArm Standard Sorting Sandbox Kit is a standardized sandbox kit designed for learning robotic arm vision recognition, color block sorting, and tag sorting. It is equipped with the NexArm robotic arm, a 3D depth camera, a metal baseplate for the standard sorting sandbox scene, a scene recognition area panel measuring 264 × 264 mm, colored plastic trays, a 7-inch touch screen, color blocks, waste/tag cards, and other modules, with an optional WonderEcho Pro AI voice interaction box. It supports OpenCV color recognition, AprilTag tag recognition, target center positioning, inverse kinematics grasping, and categorized placement of color blocks/tags. It serves as an ideal platform for studying automated robotic arm sorting and ROS application development in conveyor-free scenarios.

13.2.3 Robot Startup Instructions ​

This section covers the power-on status of the robot and functional verification of each module. After completion, proceed to subsequent chapters to learn app control.

To connect to the robot via remote tools, explore additional robot applications, and inspect programs, refer to 1. Tutorials / 1. NexArm User Manual / 1.5 Development Environment Setup and Configuration.

NOTE

The robotic arm must be secured firmly before starting. Sandbox kits must ensure the base screws are tightened. The robotic arm generates swing and inertia during startup and operation. If unsecured, it may tip over, fall, or sustain damage, and may also pose safety risks.

  1. Connect the 12 V 5 A power adapter to the ESP32 controller. Following this order ensures proper operation of all robotic arm hardware.

  2. Do not stack robotic arms to prevent locked-rotor states upon power-on, which can damage the servos.

  3. Do not operate the robotic arm under heavy loads for extended periods, as this will also shorten servo service life or cause permanent damage.

  4. Maintain a safe distance from the robot before starting to prevent injury caused by accidental contact after power-on.

  5. Push the power switch to the ON position.

Wait approximately 1 minute. The robotic arm returns to its initial posture, and the buzzer emits a short beep, indicating that device startup is complete.

NOTE

If the buzzer does not emit a short beep, a hardware issue such as a buzzer malfunction may exist. This does not typically occur under normal usage. If this happens, contact customer support for assistance.

  • Adjusting Color Thresholds
  1. Open the LAB Tool. In the color list of the recognition adjustment area, select the color requiring threshold adjustment, using red as an example here.
  1. Set the min values of the L, A, and B components to 0, and set the max values to 255.
  1. Place the colored object within the camera field of view. Refer to the LAB color space distribution diagram, and adjust the L, A, and B components toward the target color range.

Red is located near +a, so increase the A component by keeping its max value unchanged and increasing its min value until the colored object area in the left image display turns white while other areas turn black.

  1. Adjust the remaining L and B components according to the operating environment. If the red color appears lighter, increase the min value of the L component. If it appears darker, decrease the max value of the L component. If the red color has a warmer tone, increase the min value of the B component. If it has a cooler tone, decrease the max value of the B component.

In addition to the built-in recognizable colors, additional colors can be added. Taking yellow as an example, the specific operating steps are as follows:

  1. Enter the color name in the name field and click OK.

  1. Place the colored object within the camera field of view, and drag the L, A, and B component sliders to adjust thresholds until the colored object area in the left image display turns white while other areas turn black.
  1. Click Save in the recognition adjustment area to save the color threshold adjustment parameters.

NOTE

The calibration option shown in the illustration is scene_3 for the advanced sorting sandbox. The equipment used in this tutorial is scene_2 for the standard sorting sandbox. The calibration operating steps are identical and can be executed following this workflow.

  1. Select Pixel Positioning in Mode, and place the color block at the center position.

  2. Click the color block in the color calibration area with the mouse. The robotic arm automatically samples the color, recognizes the target, and executes only the grasping motion. Adjust the positioning offsets for X, Y, and Z based on the grasping results. Note that Save must be clicked after modifying values for changes to take effect.

    As shown in the figure above, adjusting the X-axis value moves the robotic arm forward or backward. For example, setting X to a positive value moves the arm forward. Adjusting the Y-axis value moves the robotic arm left or right. For example, setting Y to a positive value moves the arm to the left. Adjusting the Z-axis value moves the robotic arm up or down. For example, setting Z to a positive value moves the arm upward.

  3. After adjusting the parameters, click Save first to save and apply the configured data to the robotic arm grasping program. Next, click Home to return to the robotic arm recognition and grasping state. Finally, click the color block again with the mouse. The robotic arm automatically samples the color, identifies the position, and performs grasping.

  4. Once the color block can be successfully grasped at the center position, place the wooden block within the bounding box on the map. Click the color block with the mouse, and adjust the positioning Y Scale according to the grasping performance of the mechanical gripper. This parameter adjusts the gripper opening size along the Y-axis. Once the center block offset is properly calibrated, only the scale needs adjustment. Ensure that all four corners of the bounding box can be grasped normally.

13.6.6 Program Analysis ​

  • Launch File Analysis

The standard sorting sandbox corresponds to Scene 2, whose primary startup entry point is the color block/tag sorting program.

The color block sorting launch file is located at: ~/ros2_ws/src/app/launch/object_sorting.launch.py

python
object_sorting_node = Node(
    package='app',
    executable='object_sorting',
    output='screen',
    parameters=[{
        'start': start,
        'display': display,
        'broadcast': broadcast,
        'use_scene_pose': use_scene_pose,
        'play_config_path': play_config_path,
    }]
)

This launch file starts the object_sorting executable in the app package, located at ~/ros2_ws/src/app/app/object_sorting.py. The program recognizes color blocks or AprilTag tags via the camera, calculates grasp coordinates, and then reads target placement coordinates according to the current scene configuration.

Scene 2 also retains the waste classification entry point, with the launch file located at: ~/ros2_ws/src/app/launch/waste_classification.launch.py. When the interface switches to the waste classification application, this launch file starts yolo_node in the example package and waste_classification in the app package. Placement points for waste categories are likewise retrieved from place_targets in the Scene 2 configuration file.

  • Scene Configuration Binding

The configuration binding for Scene 2 is located at: ~/ros2_ws/src/app/app/scene_play_registry.py

python
SCENE2_ID: {
    "play_id": "color_tag_sorting",
    "package": "app",
    "launch": "object_sorting.launch.py",
    "launches": [
        {"package": "app", "launch": "object_sorting.launch.py"},

This configuration indicates that when the system is set to scene_2, it uses scene2_color_tag_sorting.yaml as the application configuration file. The fields allowed to be merged into the scene configuration for Scene 2 are as follows:

python
SCENE2_ID: ("place_policy", "place_targets", "color_grid")

Therefore, when modifying placement positions for the standard sorting sandbox, focus on place_targets. When modifying the color slot order, focus on color_grid.slots.

The coordinate format for each target under place_targets is [x, y, z], in meters. For example:

yaml
red:
- 0.01
- 0.172
- 0.06

This indicates that the red color block is placed at x = 0.01 m, y = 0.172 m, z = 0.06 m, which is approximately x = 10 mm, y = 172 mm, z = 60 mm.

The place_policy section restricts placement coordinates:

python
if bool(policy.get('only_left_y_positive', False)) and pos[1] < 0.0:
    pos[1] = abs(pos[1])

min_place_z = float(policy.get('min_place_z', DEFAULT_PLACE_POLICY['min_place_z']))
if pos[2] < min_place_z:
    pos[2] = min_place_z

In the current configuration, only_left_y_positive: true specifies that if the y coordinate of a placement point is negative, the program automatically converts it to a positive value. Furthermore, min_place_z: 0.015 specifies that the minimum placement height will not be lower than 0.015 m.

Scene 2 also configures the color slot order:

yaml
color_grid:
  slots:
  - red
  - green
  - blue
  - yellow
  slot_targets:
  - - 0.01
    - 0.172
    - 0.06
  - - 0.157
    - 0.28
    - 0.06
  - - 0.157
    - 0.172
    - 0.06

    - 0.28
    - 0.06

color_grid.slots represents the order of color grid cells, which the program uses to generate color sorting priorities. slot_targets is the list of slot coordinates, and its sequence corresponds one-to-one with slots. During actual robotic arm placement execution, object_sorting.py primarily retrieves place_targets based on target names. Therefore, when adjusting the position of a specific color, ensure that place_targets and color_grid.slot_targets remain consistent.

def priority_from_scene_config(scene_cfg):
    scene_cfg = scene_cfg if isinstance(scene_cfg, dict) else {}
    color_slots = []
    waste_slots = []
    color_slots.extend(_slots_from_grid(scene_cfg.get("color_grid"), "slots", COLOR_KEYS))
    return _unique_valid(color_slots + waste_slots)

Consequently, the sequence of color_grid.slots in Scene 2 determines which color the program prioritizes. For example, when the current order is red, green, blue, and yellow, the program coordinates sorting targets in this sequence if multiple targets appear simultaneously in the camera feed.

python
def resolve_place_position(self, target_key):
    scene_name, scene_cfg = self._load_active_scene_config()

    place_targets = scene_cfg.get('place_targets', {}) if isinstance(scene_cfg.get('place_targets'), dict) else {}
    raw = place_targets.get(target_key, self.place_position.get(target_key, DEFAULT_SCENE_PLACE_TARGETS.get(target_key)))
    if raw is None:
        return None

    pos = [float(raw[0]), float(raw[1]), float(raw[2])]

    policy = DEFAULT_PLACE_POLICY.copy()
    if isinstance(scene_cfg.get('place_policy'), dict):
        policy.update(scene_cfg['place_policy'])
    if bool(policy.get('only_left_y_positive', False)) and pos[1] < 0.0:
        pos[1] = abs(pos[1])
    min_place_z = float(policy.get('min_place_z', DEFAULT_PLACE_POLICY['min_place_z']))
    if pos[2] < min_place_z:
        pos[2] = min_place_z

    return scene_play_registry.apply_global_place_offset(pos, self.scene_config_path)

Therefore, placement positions for red, green, blue, yellow, and tag1, tag2, tag3 in Scene 2 are determined primarily by place_targets in scene2_color_tag_sorting.yaml.
